# 实盘交易系统 — 需求与风险分析

> 日期：2026-08-18（2026-08-19 更新）
> 状态：方案阶段（未动代码）

## 一、项目定位

从「回测验证」升级为「可实盘交易的多用户系统」，由 5 个模块 + 1 个定时任务组成。

## 二、已确认的关键决策

| 事项 | 决策 |
|---|---|
| 数据源 | 蛋卷 API（先拉近十年历史，之后每周增量更新） |
| 券商通道 | QMT 客户端（内置 Python 3.6，只下单）；信号计算留自有 Linux 服务器 |
| 存储 | parquet → MySQL |
| 用户模式 | 多用户；真实交易；前端含「账号管理」模块存券商资金账号 |

## 三、模块划分与数据流

```
蛋卷API(历史10年 + 每周增量) → MySQL(模块1) ──数据更新触发──→ 策略引擎(模块2, 前端配置)
                                                                     │
                                                                     ▼ 买入/卖出/不处理 + 金额(带signal_id)
用户浏览器(登录 + 账号管理) ──绑定券商资金账号──→ 模块4/5(MySQL) ←── QMT客户端(模块3) ←─┘
                                                  （Linux HTTP下发指令 → Windows QMT只下单）
```

1. **模块1 数据存储**：存宽基 K线/PE/PB/FED 及 PE/PB 滚动百分位；每天 24:00 定时更新，有更新才写；某指数更新后才触发其买入判断。HTTP：输入代号 → 返回 K线/PE/PB/PE百分位/PB百分位。
2. **模块2 买入策略**：前端配置写入后台。HTTP：输入代号 → 返回 买入/卖出/不处理 + 金额。
3. **模块3 交易执行（QMT 只下单）**：运行在 Windows QMT 客户端内置 Python，轮询模块2 信号（HTTP），`passorder` 下单，回报成交到 Linux；不参与任何信号计算。
4. **模块4 交易信息**：存成交记录 + 前端配置快照。HTTP：输入用户ID → 返回该用户全部结构信息。
5. **模块5 用户**：存账户名 + 密码；多用户隔离。

## 四、风险清单

### A. 数据源（蛋卷 API）

1. **历史数据能力存疑**：蛋卷估值接口主要给「当前估值快照」（PE/PB/PE百分位/PB百分位/股息率/ROE），不一定提供十年历史 K线 + 历史 PE/PB 日频序列。要自己算历史百分位，必须有历史序列，需先确认。
2. **FED 缺失**：蛋卷估值无股债利差。中债10年/美债10年需另找数据源。FED_only / OR / VOTE 等范式将无数据可用（最优是 PB_only，但前端若开放 FED 范式即为空）。
3. **百分位口径不一致**：蛋卷百分位是其固定窗口算法，与回测「滚动 N 年 + min_samples」口径不同 → 回测结论无法精确复现。
4. **无官方开放 API**：蛋卷接口为前端非公开接口，有反爬/限流/字段变动/失效风险，需容错 + 多源兜底。
5. **「有更新才写、写了才买」判定**：每天 24:00 拉取时需对比上一快照日期/数值判断是否有更新，否则漏触发或重复触发。
6. **代码映射 + 覆盖不全**：蛋卷用自家 index_code，需映射表；14 个指数（尤其港股通、红利类）可能不全覆盖。

### B. 券商 API（国金证券）

7. **通道已定但有待验证**：miniQMT 已不可用，改用 QMT 客户端（内置 Python 3.6，只下单）。关键残留风险：内置 Python 能否 `urllib` 网络出站（信号下发的前提）、`passorder` 对 ETF（尤其港股通/QDII）的支持。
8. **券商密码存储（高危）**：账号管理模块存券商资金账号 + 交易密码，绝不能明文；需 AES-GCM 加密 + 密钥独立管理，只在调用券商接口瞬间解密。系统登录密码另用 bcrypt/argon2 哈希。
9. **资金密码处理**：QMT 客户端登录时验证密码，`passorder` 下单通常不传密码（需确认有无二次确认）；券商账号/密码仍存于 Linux 账号管理模块，需 AES-GCM 加密 + 日志脱敏。
10. **多账号登录态**：多用户各绑账号，券商 session/token 过期需自动重连 + 失败告警。
11. **下单是异步的**：下单→已报→部分成交→全成→撤单→废单，成交回报异步；模块3「成功/失败」不能只靠同步返回，需轮询/回调。
12. **幂等（高危）**：定时任务重试/网络超时会重复下单，下单接口必须带幂等键（如 signal_id）。
13. **实盘资金风险**：真实交易，方向反了/金额错/重复下单都是真金白银损失；建议先模拟盘跑通全链路 + 金额上限 + 风控熔断。

### C. MySQL 迁移

14. **表结构**：14 指数 × 10 年 × 日频，需 (code, date) 联合主键 + 索引，必要时分区。
15. **数据回填 + 双口径并存**：现有 wind_new_merged parquet 回填 MySQL；但蛋卷新数据与旧 Wind 数据口径不一致，两套数据并存，需明确以谁为准。
16. **连接池 / 事务 / 凭证 / 备份**。

### D. 多用户 / 账号管理 / 前端

17. **前端选型（重大）**：参考页是 Next.js（AuthGuard + Onboarding + Toast），现有是 FastAPI + 静态 HTML/ECharts。沿用 FastAPI 模板 or 换 React/Next.js，决定前端工作量。
18. **权限隔离**：用户只能看自己的交易/配置/券商账号，接口需用户级鉴权。
19. **会话管理**：JWT/session 过期、刷新、登出。

### E. 架构 / 调度

20. **调度器**：每天 24:00 + 每周增量，需 APScheduler/cron/Celery，且与「信号→下单」链路解耦。
21. **状态跟踪**：哪些指数今天更新了、哪些已下单，需任务状态表，避免漏单/重单。

### F. 合规

22. **代管他人证券账户**：多用户绑定券商资金账号、系统自动下单，可能触碰「账户出借」「代客理财」监管红线；建议先咨询国金证券/法务确认合规边界。
